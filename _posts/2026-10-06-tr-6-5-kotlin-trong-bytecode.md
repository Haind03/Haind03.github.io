Open a recent Android app in JADX and you almost certainly see Java. But wait, aren't most apps written in Kotlin these days? Yes. The catch is that Kotlin compiles to the very same DEX bytecode that Java compiles to, so the decompiler reads the bytecode and rebuilds it as Java, the language it knows how to express. The original Kotlin has evaporated.

The good news: the Kotlin compiler leaves a lot of characteristic traces. Once you recognize them, you both know the code was Kotlin and can read the intent much faster instead of swimming in machine-generated Java. This lesson is that set of traces.

## Sign number one: @Metadata

Every class generated by Kotlin carries an `@Metadata` annotation at the top. In JADX you'll see something like:

```java
@Metadata(mv = {1, 9, 0}, k = 1, d1 = {"..."}, d2 = {"..."})
public final class LoginManager {
```

The `d1`/`d2` are the encoded Kotlin signature (function names, parameter types, nullability, original parameter names). Seeing `@Metadata` lets you conclude right away: this class was Kotlin. More importantly, there are tools (like jadx with a plugin, or kotlin-metadata readers) that use `d2` itself to recover the real parameter names, something Java bytecode usually doesn't keep.

## Sign number two: Intrinsics null-checks everywhere

Kotlin distinguishes nullable types (`String?`) from non-null (`String`). To keep the non-null promise at the boundary with Java, the compiler inserts automatic checks at the start of almost every function:

```java
public final void login(String user, String pass) {
    Intrinsics.checkNotNullParameter(user, "user");
    Intrinsics.checkNotNullParameter(pass, "pass");
    // ... the real code starts here
}
```

Those `Intrinsics.checkNotNullParameter` lines (and `checkNotNull`, `checkNotNullExpressionValue`) aren't the author's logic, they're compiler-generated junk. When reading, skip them and jump down to the real code. Seeing `Intrinsics.*` everywhere is one more confirmation that this is Kotlin.

## Sign number three: a data class balloons into a pile of methods

In Kotlin you write one line:

```kotlin
data class User(val id: Int, val name: String)
```

But the compiler generates a dozen methods, and JADX shows them all:

```java
public final class User {
    private final int id;
    private final String name;
    public final int component1() { return this.id; }
    public final String component2() { return this.name; }
    public final User copy(int id, String name) { ... }
    public boolean equals(Object other) { ... }   // compares field by field
    public int hashCode() { ... }
    public String toString() { return "User(id=" + id + ", name=" + name + ")"; }
}
```

The set of `component1()`, `component2()`, `copy()`, plus `equals`/`hashCode`/`toString` comparing and printing per field, is the unmistakable signature of a data class. Seeing it tells you right away this is just a chunk of data, not logic worth reading, skim past it.

## Sign number four: companion objects and extension functions

A `companion object` (where Kotlin keeps a class's static members) turns into an inner class named `Companion` with a static field:

```java
public static final User.Companion Companion = new User.Companion(null);
```

An extension function (`fun String.clean()`) has no place in the JVM, so it becomes a static method that takes the receiver as the first parameter:

```java
// Kotlin: fun String.clean(): String
public static final String clean(String $this$clean) { ... }
```

A parameter named `$this$...` is a clear sign of an extension function.

## The hardest to chew: coroutines become a state machine

This is where Kotlin makes the pseudocode messiest. A `suspend fun` looks linear in the source:

```kotlin
suspend fun fetch(): Data {
    val token = getToken()      // suspend
    val data = download(token)  // suspend
    return data
}
```

After compilation, the compiler tears it into a **state machine**: the whole function body is stuffed into a function that takes an extra `Continuation` parameter, with a `label` variable and a big `switch`. Each suspension point is a `case`. In JADX you see something like:

```java
public final Object fetch(Continuation $completion) {
    // ... restore state from $continuation.label
    switch (this.label) {
        case 0:
            this.label = 1;
            obj = getToken(this);         // if it returns COROUTINE_SUSPENDED, return right away
            if (obj == suspended) return suspended;
            break;
        case 1:
            // continue after getToken, now call download
            ...
    }
}
```

How to read it: don't try to understand the state machine mechanism. Treat `label` as a step number, and read each `case` in increasing order, which are the sequential lines in the original source. Each `case` does one thing then sets `label` to the next step. Join them together and you get the original linear logic. The `== suspended` returns are only the pause/resume mechanism, which you can ignore while tracing the logic.

## Key takeaways
- Kotlin compiles to the same bytecode as Java, so JADX shows Java. The original Kotlin is gone.
- `@Metadata` at the top of a class: definitely Kotlin, and it holds the signature for recovering names.
- `Intrinsics.checkNotNull*` is compiler-inserted junk, skip it when reading.
- A data class gives itself away through `component1/2...`, `copy`, `equals`/`hashCode`/`toString` per field.
- An extension function becomes a static method with a `$this$...` parameter.
- Coroutines become a state machine with `label` + `switch`: read each `case` in order like the sequential steps of the source.
